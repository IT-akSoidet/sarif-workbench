## ПРОМПТ 

Ты помогаешь мне реализовать `py-bookstore` — намеренно уязвимое Flask-приложение на Python для учебного проекта: сравнение SAST-анализаторов (Bandit, Semgrep, CodeQL) внутри инструмента SARIF Workbench. Это НЕ продукт для пользователей, а контролируемый эталонный набор уязвимостей с известными, задокументированными CWE в конкретных, заранее определённых местах кода.

### Контекст и ограничения

- Код должен быть **синтаксически корректным и логически связным** Flask-приложением, но НЕ обязан быть production-ready или безопасным — это намеренно.
- Каждая уязвимость должна соответствовать **конкретному CWE**, указанному ниже, и лежать **именно в том модуле**, где указано — это важно для последующей проверки через SARIF Workbench.
- Не добавляй safe/fixed-версии находок на этом этапе — только vulnerable. Safe-версии будут отдельной задачей позже.
- Не исправляй уязвимости "на автомате" из соображений best practices — это противоречит цели проекта. Если сомневаешься, оставляй уязвимый вариант и явно комментируй `# VULN: CWE-XXX — <причина>` прямо над проблемной строкой.
- Стек: **Flask + SQLite (через `sqlite3` или SQLAlchemy — на твой выбор, но будь последователен) + Docker**.
- Порт — **5050**, не 5000 (часто занят другими процессами на моей машине).

### Модель данных

```
User: id, username, password_hash, email, is_admin, secret_question, secret_answer
Book: id, title, author, description, price, cover_url
Order: id, user_id, book_id, total_price, discount, status, created_at
Review: id, book_id, user_id, text, created_at
```

В `db_init.py` — создание таблиц и сид: 3 пользователя (один — `is_admin=True`), 12 книг с разными авторами, 2-3 стартовых отзыва.

### Точная карта уязвимостей — реализуй ВСЕ 30, каждую в указанном модуле

**`app/auth.py` (8 находок):**
1. CWE-327 — хеш пароля пользователя при регистрации через `hashlib.md5()` без соли.
2. CWE-327 — токен «запомнить меня» — MD5 от `user_id` (+ что-то предсказуемое, например timestamp).
3. CWE-327 — промокод хешируется MD5 для проверки валидности.
4. CWE-347 — JWT при логине создаётся и проверяется так, что сервер принимает токен с `alg: none` (не проверяет алгоритм из заголовка).
5. CWE-347 — то же самое для refresh-токена.
6. CWE-613 — сессионная кука выставляется без `max_age`/срока действия.
7. CWE-613 — кука «запомнить меня» — та же проблема.
8. CWE-307 — эндпоинт логина не имеет ограничения числа попыток входа (ни счётчика, ни задержки, ни капчи).

**`app/search.py` (4 находки):**
9-12. CWE-89 — SQL-инъекция в ЧЕТЫРЁХ разных местах: поиск книг по названию, фильтр по автору, поиск отзыва по ID книги, проверка промокода. Везде — конкатенация или f-string пользовательского ввода прямо в SQL-запрос вместо параметризованных запросов (`?`/`:param`).

**`app/orders.py` (12 находок):**
13. CWE-639 (IDOR) — `GET /orders/<id>` отдаёт заказ по числовому ID без проверки, принадлежит ли он текущему пользователю.
14. CWE-639 — `GET /invoices/<id>` — та же проблема.
15. CWE-639 — `GET /wishlist/<id>` — та же проблема.
16. CWE-501 (Trust Boundary Violation) — при оформлении заказа `total_price` берётся из тела запроса и сохраняется как есть, без пересчёта суммы на сервере из цены книги и количества.
17. CWE-501 — размер скидки (`discount`) тоже принимается от клиента без проверки/пересчёта.
18. CWE-78 (OS Command Injection) — генерация PDF-чека вызывает `os.system()`/`subprocess` с `shell=True`, куда попадает параметр из запроса (например, имя файла или ID заказа без санитизации).
19. CWE-78 — экспорт заказов в CSV — аналогичная проблема через `os.system()`.
20. CWE-502 (Insecure Deserialization) — состояние корзины сериализуется через `pickle.dumps()` и хранится в cookie, десериализуется через `pickle.loads()` при следующем запросе без проверки источника.
21. CWE-918 (SSRF) — загрузка обложки книги по URL: эндпоинт принимает `image_url` от пользователя и делает `requests.get(image_url)` без какой-либо проверки адреса (не блокирует localhost/внутренние IP/redirect).
22-24. Оставшиеся 3 находки этого модуля — распредели как: CWE-16 (Configuration) — небезопасная настройка, влияющая на обработку заказов (например, отключена проверка CSRF на изменение заказа, если используешь Flask-WTF, или что-то аналогичное); если не находишь естественного места — перенеси эти 3 находки в `config.py` (см. ниже) и добавь вместо них ещё вариации CWE-639/CWE-78 в этом модуле, чтобы сумма по модулю осталась 12. Явно напиши мне, как ты в итоге распределил, в README.

**`app/reviews.py` + `templates/*.html` (3 находки):**
25. CWE-79 (XSS) — текст отзыва рендерится в шаблоне через `{{ text|safe }}` или аналогичный обход автоэкранирования Jinja2.
26. CWE-79 — описание товара в админ-панели (`admin.py`) — та же проблема при рендере.
27. CWE-79 — имя пользователя в шапке сайта (`base.html`) — та же проблема.

**`app/config.py` (3 находки):**
28. CWE-16 — `DEBUG=True` в конфигурации, которая помечена как "production" (например, класс `ProductionConfig`).
29. CWE-16 — дефолтный, не изменённый `SECRET_KEY` (что-то вроде `"dev-secret-key-change-me"`, оставленное как есть).
30. CWE-942 (Permissive CORS) — `CORS(app, origins="*")` или аналогичная настройка, разрешающая запросы с любого источника.

**Отдельно, без нового кода:**
- CWE-778 (Insufficient Logging) — убедись, что НИГДЕ в `auth.py` не логируются неудачные попытки входа. Это находка через отсутствие — просто не добавляй логирование туда, где интуитивно оно должно быть.

**`requirements.txt`:**
- CWE-1104 (Vulnerable Components) — зафиксируй заведомо старую версию Flask (например, `Flask==1.1.4`) и заведомо старую версию Pillow (например, `Pillow==8.0.0`). Перед фиксацией версий — если можешь проверить в интернете реальные CVE для этих версий, сделай это и укажи в README, какие именно CVE это иллюстрирует. Если доступа в интернет нет — используй указанные версии как есть и оставь пометку `# TODO: verify CVE`.

### Что нужно в итоге (definition of done)

1. `docker compose up` поднимает приложение на `http://localhost:5050` без ошибок.
2. Все 30 находок присутствуют в коде, каждая помечена комментарием `# VULN: CWE-XXX`.
3. `Makefile` с целями:
   - `make run` — поднять через docker compose
   - `make scan` — прогнать `semgrep scan --config auto --sarif --output report.sarif .` (не забудь исключить venv/`__pycache__`/`node_modules` через `.semgrepignore` или флаг, если он будет создаваться)
   - `make seed` — пересоздать БД с сидовыми данными
4. `README.md` с таблицей: CWE → файл → номер строки (примерно) → короткое описание — это будет сверяться с реальным выводом Semgrep.
5. В конце — напиши мне краткий отчёт: какие 30 находок реализованы, есть ли отклонения от этого списка и почему.

### Как действовать

Работай пошагово: сначала инфраструктура (Docker, skeleton, БД), потом auth.py, потом search.py, потом orders.py (самый большой модуль), потом reviews/templates, потом config.py. После каждого модуля — можешь коротко резюмировать, что сделано, прежде чем переходить к следующему. Если в процессе понадобится уточнение (например, SQLAlchemy или голый sqlite3, или какая-то деталь модели данных) — спроси меня, а не выбирай произвольно молча.
