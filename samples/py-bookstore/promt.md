Ты продолжаешь работу над `py-bookstore` — намеренно уязвимым Flask-приложением для сравнения SAST-анализаторов (Bandit, Semgrep, CodeQL) внутри SARIF Workbench. В проекте уже реализована и закоммичена **версия 1** — 30 находок, 15 CWE, полное описание в `README.md` и в исходном `promt.md`. Твоя задача — добавить **версию 2**: ещё 10 новых, отдельных уязвимостей, не трогая ничего из уже сделанного.
 
### Критически важное ограничение
 
**Не изменяй, не рефакторь и не "улучшай" ни одну из существующих 30 находок v1.** Их исходный код, комментарии `# VULN: CWE-XXX` и поведение должны остаться byte-for-byte такими же, как сейчас — они уже задокументированы, прогнаны через сканеры и загружены в Workbench как эталонный бейзлайн. Твоя работа — **только добавление нового кода**: новые функции, новые роуты, при необходимости новые файлы. Если для новой находки естественно было бы отредактировать существующую функцию — вместо этого создай новую функцию/роут рядом, а не трогай старую.
 
Единственное исключение — `main.py`: туда нужно добавить инициализацию `CSRFProtect(app)` (см. находку №1 ниже), это законное дополнение, не редактирование существующей логики.
 
Каждую новую находку помечай комментарием `# VULN v2: CWE-XXX` (обрати внимание на суффикс `v2` — так на ревью сразу видно, что это новая партия, а не часть исходных 30).
 
### Точная карта 10 новых находок
 
**1. CWE-352 (CSRF) — "оживить" уже существующую мёртвую находку.**
В `config.py` уже есть `WTF_CSRF_ENABLED = False`, но она ничего не отключает, потому что `Flask-WTF` нигде не инициализирован. Добавь в `main.py`, внутри `create_app()`:
```python
from flask_wtf import CSRFProtect
csrf = CSRFProtect(app)
```
Добавь `flask-wtf` в `requirements.txt` (зафиксируй версию, совместимую с Flask 1.1.4 — если не уверен в точной версии, поставь `Flask-WTF==0.14.3` и явно отметь в README `# TODO: verify compatibility`). После этого изменения существующая `WTF_CSRF_ENABLED=False` из v1 становится настоящей, эксплуатируемой уязвимостью — сама форма отзыва в `book.html` уже не содержит `csrf_token`, так что цепочка замкнётся сама.
 
**2. CWE-22 (Path Traversal).**
Новый роут в `orders.py`: `GET /orders/<int:order_id>/download` с query-параметром `?file=`. Читает файл из `/tmp/` по имени, полученному от пользователя, без проверки на `../`:
```python
# VULN v2: CWE-22 — path from query param used directly, no sanitization
filename = request.args.get("file", "")
path = "/tmp/" + filename
return send_file(path)
```
 
**3. CWE-434 (Unrestricted Upload).**
Новый роут `POST /books/<int:book_id>/cover/upload` в `orders.py` (соседствует с уже существующим `set_cover`, который принимает URL — это тот же функционал, но через реальный файл): принимает `multipart/form-data`, сохраняет присланный файл в `static/uploads/` **без проверки расширения или MIME-типа**.
 
**4. CWE-522 (Insufficiently Protected Credentials).**
Новая таблица `payment_cards` в `db_init.py` (добавь `CREATE TABLE`, не трогая существующие) — колонки `id, user_id, card_token`. Новый роут `POST /payment/save-card` в новом файле `app/payments.py`, который сохраняет присланный токен карты **в открытом виде**, без шифрования. Зарегистрируй новый blueprint в `main.py`.
 
**5. CWE-798 (Hardcoded Credentials).**
В том же новом `app/payments.py` — захардкоженный ключ платёжного шлюза:
```python
# VULN v2: CWE-798 — payment gateway API key hardcoded in source
PAYMENT_GATEWAY_API_KEY = "sk_live_51H8xJ2KZvQ9mF3nR7pL4tW6"
```
(используй заведомо фейковый, нерабочий ключ такого вида — не настоящий).
 
**6. CWE-640 (Weak Password Recovery Mechanism).**
Новые роуты в `auth.py`: `POST /password-reset/request` и `POST /password-reset/verify`. Используют уже существующие в модели поля `secret_question`/`secret_answer` (они засеяны в `db_init.py`, но сейчас нигде не используются). Проверка ответа на секретный вопрос — без ограничения числа попыток, без задержки, прямое сравнение строк.
 
**7. CWE-306 (Missing Authentication for Critical Function).**
Новый роут `POST /admin/books/bulk-delete` в `admin.py` — принимает список ID книг и удаляет их все, **вообще без проверки аутентификации или `is_admin`** (ни `@login_required`, ни ручной проверки сессии — просто отсутствует).
 
**8. CWE-915 (Mass Assignment).**
Новый роут `POST /profile/update` — либо в `auth.py`, либо в новом `app/profile.py` (на твой выбор, но зарегистрируй blueprint, если новый файл). Напрямую применяет весь JSON из тела запроса к записи пользователя в БД:
```python
# VULN v2: CWE-915 — entire request body applied to user record, including
# fields the client should never control (e.g. is_admin)
for key, value in data.items():
    update_user_field(user_id, key, value)
```
 
**9. CWE-611 (XXE).**
Новый роут `POST /admin/books/import` в `admin.py` — принимает XML-файл со списком книг для массового импорта, парсит через `xml.etree.ElementTree.parse()` **без отключения внешних сущностей** (то есть без `defusedxml` и без явного отключения `resolve_entities`).
 
**10. CWE-117 (Log Injection) — эволюция находки CWE-778 из v1.**
В v1 отсутствие логирования неудачных попыток входа было намеренной находкой "через отсутствие" (в `auth.py`, помечено `# VULN: CWE-778`). Не удаляй и не трогай этот комментарий. Вместо этого **добавь новую строку логирования рядом** (это не редактирование старой находки, а новый код около неё) — но реализуй её тоже уязвимо:
```python
# VULN v2: CWE-117 — username logged without sanitizing newlines/control
# characters; attacker-controlled username can forge extra log lines
logging.warning(f"Failed login attempt for username: {username}")
```
В README отметь явно: «CWE-778 (v1, отсутствие логирования) сознательно оставлена нетронутой; CWE-117 (v2) — это отдельная, новая находка о том, что если логирование всё же добавить не подумав, оно тоже может быть уязвимым».

### Как действовать
 
Сначала прочитай текущий код (`app/*.py`, `README.md`), чтобы понять существующие соглашения по стилю (голый `sqlite3`, blueprint-структура, докстринги модулей) и не выбиваться из них.
